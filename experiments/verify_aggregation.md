# 多会话带宽聚合验证方法论

> 适用项目：校园网多会话带宽聚合研究（开源镜像仓）
> 文档性质：实验方法学 + 验收判定标准，供复现与审计使用
> 数据脱敏承诺：本文档所有实测结论均以"相对倍数 / 量级区间"表述，不出现任何真实 IP、MAC、账号、SSID 或精确速率数值

---

## 1. 概述与验证目标

本文档描述**如何可靠地验证"多会话带宽合并是否生效"**。验证的完整链条是：

```
会话建立（多接口/多 MAC 各自认证）
  → 单会话速率观测（每个桶的档位）
  → 聚合通道组网（轮询/负载均衡覆盖全部会话）
  → 聚合总带宽测定（多流并行打在多个会话上）
  → 对照组判定（单会话基线 vs N 会话并行）
  → 结论分级（聚合生效 / 部分生效 / 未生效）
```

适用前提（不满足则验证无意义）：

- 每个会话**独立认证、独立在线**：会话身份 =（账号, NAS, 设备 MAC, 分配 IP, 会话 ID），每接口/每 MAC 各建立一条在线会话；
- 限速按**会话（限速桶）**独立执行，而非按账号聚合（若在账号层聚合，N 会话不会带来 N 倍总带宽，这本身正是本方法要区分的两种情形）；
- 聚合通道（负载均衡组 / TUN 接管 / 显式源地址绑定）**真实覆盖被测流量**。

## 2. 前置条件检查（先于一切测速）

开始测速前，先用下面的清单确认"多个会话确实同时在线且独立"，否则后续测得再快也不能归因于聚合：

| 检查项 | 方法 | 通过标志 |
|---|---|---|
| 每会话独立认证 | 逐接口/逐网卡依次完成认证，观察认证日志 | 每接口均有独立的认证成功事件 |
| 每会话独立源 IP | 各接口 `ipconfig` / `ip addr` | 每个会话对应一个不同的链路内 IP |
| 每会话独立出口 | 各会话内分别访问一次"查出口 IP"服务 | 出口公网 IP 各不相同 |
| 并发未超限 | 认证全部完成后立即测连通性 | 无"在线设备数已达上限"类拒绝 |
| 聚合通道就绪 | 负载均衡组配置检查、TUN 是否接管 | 规则匹配命中聚合组，且轮询名单含全部会话出口 |

> 若其中任一项不满足（例如多个接口虽在线但出口相同、或 TUN 未接管导致流量全走单一会话），后续聚合测试必然失败，先修复组网再验证。

## 3. 单会话实时速率观测（方法 a）

目的：**分别观测每个会话的实时速率**，确定"单桶档位"与"流是否真的落在对应会话上"。

### 3.1 接口速率统计（最直接的观测）

按接口（网卡）纬度统计速率，即按会话纬度统计：

- **宿主机（Windows）**：任务管理器"性能→以太网/WLAN"实时曲线；脚本化方案为读取网卡计数器做差分，例如每秒读一次已接收字节计数，`速率 = (B[t] - B[t-1]) / 1s`；
- **客户机（Linux/桥接 VM）**：`/proc/net/dev` 差分，或 `nload` / `bmon` 等实时工具；
- **无界面节点（软路由 / OpenWrt）**：`ifstat`、`vnstat -l`。

注意：

- 接口速度 = 该接口**全部流量**的合计，测试期间应独占该接口（关闭其他网络应用）；
- 差分采样周期 ≥ 1 秒，太短会因内核计数粒度抖动；
- 接口速率只能证明"这个会话在跑多少"，无法证明"流量是否被正确打散"——那需要 3.2。

### 3.2 代理连接面板 / 连接观测（证明"打散"）

聚合形态下（负载均衡组 / TUN），用连接级视图确认**并发流确实交替落在不同会话的出口上**：

- **代理连接面板**：mihomo / Clash 系内核提供实时连接面板，列出每条活动连接的目的地址、来源地址与当前下载速率。判据：N 会话聚合测试期间，面板中应同时出现**源自 N 个不同源地址**的连接流，且速率分布大致均衡；
- **`netstat` 周期采样**：每隔 1~2 秒采样一次活动连接，按本地地址（会话源 IP）分组统计连接数。稳定轮询时各源 IP 的连接数应近似均匀；
- **出口 IP 抽样**：取面板中不同源地址的若干条连接，比对其实际出口公网 IP 是否各属不同会话——这是"轮流交替出网"的直接证据。

### 3.3 逐秒吞吐曲线（判断限速形态与确定稳态窗口）

对**单条连接**做逐秒采样（每秒记录累计下载字节数的差分），得到吞吐曲线。曲线用于回答三个问题：

1. **平台值**：慢启动期后的稳态速率是多少？（= 该会话/该对端限制下的档位）
2. **形态**：是"平滑爬升到平台即封顶"（整形/固定档位特征），还是"先冲一波再回落"（突发令牌桶 / PIR > CIR 特征）？形态影响后续判定口径；
3. **稳态起点**：从第几秒进入平台？——用于确定聚合测试的"有效时长"与丢弃冷启动窗口的边界。

## 4. 聚合总带宽测定（方法 b）

目的：测定 **N 会话并行时合计能跑到的总速率**。

### 4.1 多线程并行下载（主方法）

- **并发路数**：建议 **N ≥ 8 路**（N 为会话数；若会话数较少，取 ≥ 4 路）。连接数必须**显著多于会话数**，否则轮询在少量连接间交替不稳定，无法打满各桶；
- **多源交叉**：把并发流分配到 **≥ 2~3 个不同测速对端**（知名厂商公开安装包 / 镜像站 / 测速服务），避免"单对端自身连接级限速"被误判为会话瓶颈；
- **单源多切片（可选增强）**：对同一大文件按字节段切片并发下载，两段完整拼回后做哈希校验，可同时验证"字节级无丢无错"；
- **汇总口径**：总速率 = Σ(各路成功字节) / 时长。时长的保守取法是**最后一路完成时刻**（对应脚本中的"最大耗时"口径），它比瞬时总和略低但稳定可复现。

参考的并行执行逻辑（伪代码，实现语言不限）：

```
对 i in 1..N:
    启动任务 i：经聚合出口下载 <测速源[ i mod 源数 ]>，记录(字节, 耗时)
等待全部任务（设置全局超时）
汇总：总字节 = Σ 字节；总耗时 = max(各任务耗时)
输出：总速率 = 总字节 × 8 / 总耗时
输出：逐路明细（每路速率），用于检查是否“均分”到各会话
```

### 4.2 独立测速工具交叉验证（辅方法）

- 使用支持**多线程**的公开测速 CLI（例如以 8 线程并发为默认档位的官方客户端）作为独立交叉验证；
- 测速节点选择要留意：某些节点路由质量差或无响应会造成 0 结果/低结果，需多节点比对并剔除异常节点；
- 测速工具结果与 4.1 手工多线程结果应互为印证（差距 > 30% 时需排查工具是否走了预期出口）。

### 4.3 时长与取样注意事项

| 事项 | 要求 | 原因 |
|---|---|---|
| 单轮时长 | ≥ 15 秒（覆盖慢启动 + 稳定平台） | 太短只测到慢启动爬升段 |
| 轮数 | 同场景 ≥ 3 轮，取中位数 | 抑制网络抖动 |
| 冷启动窗口 | 丢弃前 3~5 秒 | 慢启动/冷缓存会拉低均值 |
| 口径一致性 | 报告时注明"全程字节/全程耗时"还是"稳态均值" | 两种口径结果不同 |
| 背靠背 | 基线测试与聚合测试在同一时段紧邻进行 | 减小时段性波动对"对照组"的污染 |

## 5. 对照组设计（方法 c）：区分"单会话瓶颈"与"聚合成功"

聚合成立与否的本质判据来自**对比**，必须设计好对照组：

- **对照组一（单会话基线）**：同对端、同文件的**单连接**速率——代表"单个桶在当前链路与对端下的上限"；
- **实验组（N 会话并行）**：同对端、同文件的 N 路并发（或 N×M 路），全部经聚合通道打散到 N 个会话；
- **无效对照（关键）**：N 路并行但**全部显式绑到同一个会话出口**（单桶受 N 路流）——这一组用于证明"提升来自会话数而非并发连接数"。若实验组与无效对照组总速率接近，说明桶在账号层共享，聚合未生效。

控制变量清单（对照有效性要求）：

- 同一时段（背靠背）；
- 同一测速对端、同一文件或同尺寸切片；
- 代理/聚合通道开关状态一致（若开 TUN，则基线与实验组都经同一通道）；
- 被测期间无其他大流量应用干扰；
- 每轮间隔留出冷却时间，避免上一轮 TCP 连接残留影响下一轮。

## 6. 判定标准（方法 d）

以"相对倍数"表述，消除档位绝对值带来的脱敏负担：

### 6.1 判定表

| 观测结果（N 会话总速率 vs 单会话基线） | 判定 | 解读 |
|---|---|---|
| ≥ 1.5× 且接近 N 倍（如 0.8N ~ 1.0N 区间） | **聚合生效** | 各桶分别打满，合并生效 |
| > 1.5× 但明显 < N 倍 | **聚合部分生效** | 有桶未打满：查连接分布、对端限制、上联瓶颈 |
| ≈ 1.0×（1.0 ~ 1.3×） | **聚合未生效 / 账号级聚合限速** | 桶在账号层共享，或流未打散（见 7 常见陷阱） |

### 6.2 附加佐证项（非必需，但增强可信度）

- 逐会话速率接近且都处于该会话单跑档位附近 → "各桶分别生效"的直接证据；
- 峰值冲到"单会话 × N"的物理上限附近 → 说明链路上限由聚合后的 N 桶合计决定；
- 双通道单文件切片场景：合并后哈希与整包一致 → 证明并行切分无字节错位。

### 6.3 判定示例（脱敏口径）

> 实测结论一律写成："双会话总速率约为单会话的 **1.7~1.9 倍**，速率绝对量级为数十 Mbps 档位"，而非任何精确数值或真实标识。

## 7. 常见陷阱与排除指引

| # | 陷阱 | 现象 | 排除方法 |
|---|---|---|---|
| 1 | 对端自身单连接限制 | 单连接平台值远低于会话档位（如仅约 1/3） | 换 ≥2 个对端交叉验证；用多线程特性对端做基线 |
| 2 | 流不够多，轮询打不散 | 聚合值与单会话相近 | 并发路数加到 ≥4×会话数 再测 |
| 3 | 默认路由等价不均衡 | 连接虽多但全挤在单一口 | 到连接面板核对各源地址分布；显式按源地址绑定或启用 TUN |
| 4 | 单 TCP 流只能走单接口 | 单文件单连接永远只有单会话速率 | 单文件利用多会话需 Range 切片 + 并发合并 |
| 5 | 对端不支持 Range | 切片请求失败/退化为整包 | 改用多文件 / 多 URL 方案 |
| 6 | 共享上联饱和 | 聚合后总速率上升但 < N 倍，且逐会话被摊薄 | 确认上联物理带宽是否 ≥ N×档位；换非高峰时段复测 |
| 7 | 测速节点选服异常 | 工具 0 值/异常值 | 多节点比对，剔除路由差节点 |
| 8 | 会话掉线（偶发） | 某口瞬时出网失败后自愈 | 逐秒对齐采样中单独标记异常秒，不计入稳态均值 |
| 9 | 经代理测腿时的 DNS 解析方式错误 | 走聚合适配器测单腿时连接全部失败（如 HTTP 000），误判该腿已死 | 若聚合端开启了 fake-ip 类 DNS 接管，SOCKS 本地解析（socks5）会把目标解析进保留网段造成假死；改用远端解析模式（socks5h）或直连采样复核 |
| 10 | 反复下载同一文件被内容侧限流 | 逐轮绝对值逐组走低，且降幅与聚合配置无关 | 内容分发源会对短时重复下载限流；上限验证需换"冷目标"（未下载过的文件/镜像）复测，不要用同一 URL 连测多轮 |
| 11 | 出口地址漂移被误判为"换腿" | 会话重建后出口公网 IP 变化 | 运营商级 NAT 出口按会话动态分配，会话重建后出口 IP 变化属正常池重分配；判定腿是否换桶应以会话/源地址为准，不要用出口 IP 是否变化 |
| 12 | 对国际/特定目标限速的链路 | 用国外源测聚合，总值远低于预期 | 部分链路对国际流量限速，用国外源验收会误判聚合失效；验收对端应选用国内多线程能力的 CDN（见 §4.1），国外源只作连通性参考 |

## 8. 数据记录与脱敏规范

- **一律记录相对结论与量级区间**：`N 会话总速率 ≈ 单会话 × (k1~k2)`；绝对速率仅允许"数十 Mbps 档位"这类量级描述；
- **禁止出现**：真实 IP、真实 MAC、真实账号、SSID/网络名、出口公网 IP、认证服务器地址、任何精确速率数字；
- 原始脚本与日志属于不对外公开的材料，不得随文档提交；如需提交脚本请按脱敏规范改写（见《00_脱敏与贡献规范.md》）；
- 表格、曲线图如需配图，坐标轴只标相对倍数或量级区间。

## 附录 A：可复现的验证流程（逻辑级）

按下列步骤组织一次完整验证（每一步的记录都按第 8 节脱敏）：

1. **会话清点**：逐一确认 N 个会话在线且独立（第 2 节清单）；
2. **单管摸底**：对每个会话的打底出口，各取一个定长 Range 切片做单连接计时；同时做一条不经任何会话的直连对照——得到每会话的"档位级"基线（记录为量级）；
3. **单会话基线**：同对端单连接完整下载，记录单桶平台值（量级）；
4. **聚合实验**：N×M 路并行（见 4.1），期间用连接面板/`netstat` 采样确认打散（3.2）；
5. **无效对照**：同并发但全部显式绑单一会话出口（5）；
6. **交叉验证**：独立测速工具 8 线程复测（4.2）；
7. **逐秒曲线**：任一场景补一条单连接逐秒吞吐曲线确认平台形态（3.3）；
8. **统计分析**：每种场景 ≥3 轮取中位数 → 按第 6 节判定表给结论；
9. **归档**：按 8.1 格式输出脱敏结果表，原始数据保留在本地，不随文档提交。

### A1 并行聚合实现的通用形态（伪代码）

```
RANGE = 定长切片字节数（如 40MB 级）
URLS  = [ <测速源甲>, <测速源乙>, <测速源丙> ]   # 多源交叉
FUNC GetFlow(proxy, from, len):
    计时下载 URLS[轮询取模], 记录 (秒, 字节)
# 每会话直连档位：对每个会话出口执行一次 GetFlow(直连)
# 聚合实验：并发启动 N×M 个 GetFlow(聚合出口)，等待全部完成或超时
# 汇总：总速率 = Σ字节 × 8 / 最慢任务耗时
```

### A2 双通道单文件合并校验（可选场景）

```
文件按字节段切半（段 A / 段 B）
并发执行：段 A 走会话 甲 的源地址 + Range 区间；段 B 走会话 乙 的源地址 + Range 区间
完成后字节级拼接 → 计算哈希 → 与整包单通道下载的哈希比对
```
