# 03 · 限速机制与等效带宽

> 如何确认"限速按会话生效"，如何建立并验证"N 个会话 ≈ N 倍单会话带宽"的等效带宽模型。
> 本文只讲**观测方法、证据推理与通用模型**，所有环境值一律以占位符与相对倍数表达。

## 1. 先回答问题：为什么需要先搞清限速粒度

多会话聚合的全部收益，都建立在一个前提上：

> **限速的计量单位是"会话"，而不是"账号"或"物理设备"。**

- 若限速按**账号**聚合：同一账号开 10 个会话也是 1 份带宽，聚合无意义。
- 若限速按**会话**独立：N 个互不共享的会话并行，等效带宽理论上限 ≈ N × 单会话上限。

因此在动手做任何聚合工程之前，必须先用实验确认限速粒度。本节给出可复用的观测方法论。

## 2. 单会话限速的观测方法（测速方法论）

### 2.1 对端选择：多源交叉验证

限速结论必须能排除"对端服务器自己不给力"这一干扰因素。建议：

- **至少选 2–3 个相互独立的测速源**：一个到国际测速平台的官方 CLI 节点，一个到国内互联网厂商的软件分发 CDN，一个到即时通讯类应用的安装包 CDN。
- 三个源测出的合计均封顶在同一水平 → 限速发生在**本侧网络设备**上，与对端无关。
- 注意 CDN 自身的"单连接限流"是常见陷阱：有些 CDN 对单条 TCP 连接有更低的档位（实测约为单会话上限的 1/3），这**不是网络限速**，不能用单连接结果直接下结论（见 §6）。
- 淘汰路由差、无响应、选服异常的节点；优先使用测速平台官方 CLI 而非第三方 GUI/网页版，官 CLI 自带多线程与稳定选服。

### 2.2 多线程：区分"单连接限速"与"会话聚合限速"

关键对比实验是**同一对端下，单连接 vs 多连接**：

| 场景 | 读法 |
|---|---|
| 单连接（单 TCP 流） | 看单流能否爬升到平台值 → 判断"单连接配额"是否存在 |
| 8 路并行（8 条 HTTP Range 同时下载） | 看合计 → 判断"会话聚合配额"是否存在 |

典型结果有两种可能：

- **每连接限速**：8 路并行合计 ≈ 8 × 单连接，说明配额在连接级（少见）；
- **会话级聚合限速**：单连接与 8 路合计封顶在同一水平，多开只是均分（常见，即本次研究对象）。

只要"多开会把同一份总量均分"，就说明桶在**会话层**——这正是聚合的前提证据。

### 2.3 时长与采样：看平台形态

- 单次测量至少持续 **10–15 秒**，让 TCP 慢启动充分爬升后再进入平台段。
- **逐秒采样吞吐曲线**（自写采样脚本，每秒记录累计字节差），观察曲线形态：
  - **平滑爬升后稳定封顶** → 无明显突发脉冲 → 接近"固定承诺速率（CIR），突发上限≈承诺速率"的整形器；
  - **先冲一波再回落** → 存在高于承诺速率的突发能力（PIR > CIR），是另一种令牌桶形态。
- 平台值**稳定不抖动** → 整形（shaping/CIR）；平台值**来回摆动** → 更像竞争（contention）或对端波动。

### 2.4 多次取样与注意事项

- 同一场景至少 **3 次取样**，取平台段的中位/均值；只测一次可能撞上 CDN 瞬时限流或网络波动。
- 上、下行分别测：校园网套餐上下行通常**独立且不对称**，比例固定（实测下行/上行为 5:1 且上行几乎逐测一致）→ 固定档位的"承诺速率"，而非动态竞争。
- 测试期间**退出一切代理/VPN 类客户端**，否则测到的是代理链路而不是校园网。
- 测试期间不要做任何接口变动（增删网卡、重启网络），避免触发现有网络的"变动惩罚"污染数据面（见文档 04）。
- 记录测试对端与并发数，保证多次取样条件一致。

### 2.5 有线 vs 无线对照（补测设计）

同一台设备的**有线口与无线口分别独立认证**后，各自是一个独立会话：

- 先测各自的单会话上限（应一致 → 限速档位与介质无关）；
- 再**同时**从两个会话并发下载，看合计 → 这是"会话级限速"最直接的证据（见 §3.3）。

## 3. "限速按会话生效"的观测证据与推理

设单会话下行上限为 **C**（通用符号，不指代任何具体数值）。以下证据均以倍数/百分比表达。

### 3.1 证据一：单连接与多连接合计一致（≈ 1.0×C）

- 单连接从某分发 CDN 下载：平滑爬升后封顶 ≈ 1.0×C → 单流可以吃满整个会话配额；
- 同一对端 8 路并行：合计也 ≈ 0.96–1.0×C，8 条流均分（各约占 1/8）。

**推理**：限速不是"每连接"，而是"每会话一个总量桶"。多开下载器、浏览器多线程都不会突破，只是把桶内份额切得更碎。

### 3.2 证据二：单流能否吃满取决于对端，但上限不变

一个对端单连接只有 ≈ 0.3×C（CDN 侧限流），另一个对端单连接能爬满 ≈ 1.0×C。**换对端只改变单流的可达高度，不改变会话合计上限**。→ 上限由本侧网络设备决定，与对端无关。

### 3.3 证据三：有线/无线同档位，双会话各自独立（合计 ≈ 2.0×C）

- 有线单会话 ≈ 1.0×C；无线单会话 ≈ 1.0×C → 档位与介质无关；
- **有线 + 无线两会话同时并发**：合计 ≈ **1.98×C** —— 两个会话各自拿满一份，互不共享。

**推理**：若按账号聚合，双会话合计应仍为 1.0×C；实测 ≈ 2.0×C 直接证明限速**按会话独立计量**，账号名下多个会话就是多个独立桶。这是全部分聚合收益的来源。

### 3.4 证据四：上下行独立、固定比例（固定档位）

下行 ≈ 1.0×C、上行 ≈ 0.2×C，比例稳定且上行数值逐测精确一致 → 典型的**固定承诺速率档位**（CIR），而非浮动竞争；若为竞争，上行会随负载波动。

### 3.5 证据五：平台稳定、无突发（整形而非竞争）

多源、多次、逐秒采样的平台值稳定不抖动，且无"先冲一波"的 PIR 突发 → 形态上接近 **CIR≈PIR 的令牌桶整形器**，由认证会话建立时在网关/AAA 侧的会话层下发。这与"限速随认证会话生效、与接口/端口/网段无关"完全自洽。

### 3.6 证据六：账号套餐档位吻合（来源确认）

实测平台值与账号所办套餐档位一致（下行 C、上行为 C 的 1/5）→ 限速来源是**账号套餐档位**，认证成功后按会话执行。

### 3.7 推论小结

> 认证权限与限速策略都**按会话绑定**：每个接口/设备独立认证 → 独立会话 → 独立的桶与放行 ACL。
> "并发设备数"决定能同时在线几个会话，"限速档位"决定每个会话跑多快 —— 两者是正交的两个维度。

## 4. 等效带宽模型

### 4.1 模型定义

设单会话下行上限为 C，聚合系统同时持有 N 个独立、互不共享的在线会话，则：

```
等效带宽上限 ≈ N × C        （当 N 个桶全部"满额在线"且都能跑满时）
```

聚合含义："把同一份任务（下载、浏览、流媒体）的连接/分片**分布到多个桶**"，让每个桶都按自己的 C 满负荷工作，再在出口侧合并。N 越大理论上限越高。

### 4.2 实测趋势（相对倍数）

| 会话数 | 实测趋势（相对单会话） | 说明 |
|---|---|---|
| 1 | 1.0× | 基准 |
| 2（双介质：有线 + 无线） | ≈ 1.98× | 双会话各自满额 |
| 2（单根物理线 + 虚拟多接口） | 稳态 ≈ 1.86×，峰值可达 1.09 倍物理线速 | 共享一根物理线，稳态略低于理论 |
| 3（跨账号/混合认证路径） | ≈ 3.0×（约 1.03×理论） | 三会话并发实证 |
| 含突发（PIR）时 | 短暂可达理论值的约 1.1–1.2× | 超出部分是突发余量，非稳态 |

规律：**会话数翻倍，等效带宽近似翻倍**；突发窗口内可短暂略超理论值。单根物理线共享的形态，稳态增益略低于独立介质（约 93%），但峰值仍可逼近甚至略超线速。

### 4.3 实际增益的制约因素

理论上限 N×C 在真实环境受四类制约，实际取值通常是：

```
实际增益 ≈ min( N×C, 出口上联剩余容量, 对端能力, N'×C )
```

其中 N' 是"同一时刻真正能满额跑"的会话数（受哈希分布影响）。

1. **对端能力**：CDN 单连接限流、对端单 IP 连接数限制、瞬时限速。对端不给流量时，桶满不上去。
2. **出口上联链路**：多个会话共享同一上联/同一出口设备。上联接近饱和时，各桶叠加失效——此时瓶颈从"会话桶"转移到"物理链路"。
3. **哈希碰撞（分流均匀性）**：用 multipath/负载均衡把连接分布到各会话时：
   - L3 哈希（仅源/目的地址）：同目标（如同一个 CDN 域名解析出的少数 IP）的所有连接会全部命中同一会话 → 实际增益退化为 ≈ 1×N 的幻觉；
   - **L4 哈希（含端口）**：才能把并发连接均匀打散到多个桶，让 N 个桶同时满额。
   - 实测对照：L3 哈希下两条会话的流量比可达 1:300+，切到 L4 后恢复近 1:1。**这是"配了聚合却没提速"最常见的原因。**
4. **会话并存规则**：并发名额上限、同账号互斥（同类型会话"后到顶先到"）、变动惩罚窗口（见文档 04）。N 能维持多大，取决于账号规则与运维纪律，而非模型本身。

### 4.4 单文件能否享受聚合

单条 TCP 连接只能绑定一个源地址 → 单流永远只走一个桶（上限 = C）。要让**单个文件**享受 N×C：

- 按字节段切片 + 显式绑定不同会话（源接口/源地址）+ 对端支持 HTTP Range，分片下载后合并；
- 双通道单文件实测：耗时约减半、合并后字节级一致（校验哈希与整包下载相同）；
- 或依赖应用自身的多连接特性（流媒体分片、浏览器并发资源、多线程下载器），由连接级负载均衡自动分布——多数日常场景不需要单流聚合。

## 5. 等效带宽的验证方法（防止"以为自己聚合了"）

- **并发测速**：8 路并行下载看合计是否 ≈ N×C；单连接采样**不能**用于判断聚合是否生效（单连接天然只走一个桶，结论永远"没聚合"）。
- **逐会话观测**：同时观察 N 个桶各自的实时速率，看是否都接近 C、"近似叠加"。
- **出口交替检查**：多连接轮询采样出口地址，确认连接被分布到不同会话（若出口侧按账号聚合同一出口，则以**带宽叠加**为准）。
- 多次取样、控制变量，与 §2 的方法论一致。

## 6. 常见误判清单

| 误判 | 真相 |
|---|---|
| "单连接只有 1/3 上限，网络限速太低" | 对端 CDN 的单连接限流，换支持大单流的对端即可吃满会话配额 |
| "单连接测速 1.0×C，说明没聚合" | 单连接只能走一个桶，判断聚合必须并发测速 |
| "多开下载器总量还是 C，聚合无效" | 未把连接分布到多个会话（哈希碰撞 / 未绑定 / 单一出口路由） |
| 测速值忽高忽低 | 测试期间有接口变动触发了网络侧惩罚 / 冷却（见文档 04） |
| 上行比下行低很多"不正常" | 校园网套餐普遍上下行独立不对称、固定档位，实测比例天然如此 |

## 7. 小结

- 用 §2 的方法论（多源、多线程、时长足够、多次取样、有线无线对照）可以干净地确认："**限速按会话独立生效**，单会话上限 C，上下行固定比例，形态为会话层整形"。
- 在此基础上，等效带宽模型成立：**N 个独立会话并行 ≈ N×C**，实测双会话 ≈ 1.98×、三会话 ≈ 3×，突发窗口可短暂略超。
- 实际增益由对端能力、出口上联、L4 哈希均匀性共同钳制；**先解决分流均匀性，再谈叠加上限**。
