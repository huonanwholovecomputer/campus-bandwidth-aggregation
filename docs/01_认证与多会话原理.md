# 01 校园网认证与多会话原理

> 开源项目《校园网带宽聚合研究》· 原理篇 01
> 本文由内部调研资料脱敏重写，仅讨论认证与会话机制的通用原理；文中 MAC、IP、账号、速率均为占位符或示意值，不指向任何真实环境。

## 0. 术语约定

| 术语 | 含义 |
|---|---|
| NAS / BRAS | 接入认证网关：负责终端接入识别、会话建立与数据面放行策略 |
| Portal | 重定向式认证门户页面 |
| 白名单 | 账号下"免密放行"的设备 MAC 集合（无感列表） |
| 会话 | 一次认证成功后形成的在线单元，携带独立的限速与计费属性 |

## 1. 认证模型：账号—设备（MAC）绑定

### 1.1 一次典型认证的完整链路

1. 未认证终端发起 HTTP 访问 → 网关强制重定向到认证门户，并在重定向过程中通过**网关与门户之间的私有信任通道**携带该终端的真实内网 IP 与 MAC；
2. 用户提交账号密码 → 门户向账户中心校验（如目录服务）→ 通过后为"该 MAC + 该内网 IP"建立在线会话；
3. 数据面放行由网关硬件策略执行，认证接口只是控制面入口。

要点：

- **会话上下文 =（内网源 IP，MAC，账号）三元关联**，且该上下文只能由"被网关强制重定向"的链路产生。脱离这条链路的"伪认证"（例如从外部直连调用认证接口、伪造来源 IP 头）无法取得完整上下文，会被网关拒绝——这是"认证不能简单脚本化"的根因。
- 认证类接口与"查会话 / 查白名单"类接口的上下文要求不同：前者要求请求源位于被管理的会话链路内，后者通常只读取报文中的业务字段。两类接口由此产生安全水位差异，与本篇 §2.4 的风险场景直接相关。

### 1.2 设备白名单与无感（免登录）认证

- 账号可将设备的 MAC 登记进白名单；登记动作要求**账号密码**（绑定侧为"账号 + 密码 + MAC"三方校验）。
- 此后该 MAC 接入时，网关命中白名单即**直接免密放行**（放行侧只看 MAC 单因子），无需再次认证——即"无感 / 免登录"。
- 两侧因子不对称（**绑定要凭据，放行只看 MAC**）是这一类系统的共同特征，也是"MAC 克隆可免密"与"绑定可被静默删除"两个风险方向的根源。

无感认证的工程价值：

- 设备**断线重连零人工**（开机即自动恢复在线会话）；
- 支撑"断电 → 来电 → 自动恢复"的全自动化运维。

### 1.3 账号下的多设备、多会话并存

- 账号通常持有一定数量的**并发名额**（会话配额）：同一账号可同时在线多台设备，但总数受配额约束。
- 服务端按终端类型（PC / 移动端）分别维护配额池，类型由前端按浏览器 UA 上报归类。
- 调研归纳的行为规则（不同实现各有差异，以下为本次调研观察）：

  1. 同一账号的**无感会话之间在同一个接入端口上互斥 / 顶替**：后接入的无感设备会顶掉先接入的同账号无感会话；
  2. **手动认证会话与无感会话可以共存**：认证轨之间的互斥弱于"无感轨内部"，因此一个账号实际常用的并行组合是"1 条手动认证轨 + 1 条无感轨"；
  3. 跨账号的会话彼此独立、互不干扰。

结论：多会话并存是认证系统**原生支持**的业务能力（多台设备各自形成会话），只是同一账号下存在名额与顶替规则，需要工程上规避（见第 3 节）。

## 2. 会话生命周期：上线、续期、回收与主动下线

### 2.1 上线

- 手动认证：重定向链路内输入凭据 → 会话建立。
- 无感认证：MAC 命中白名单 → 免密上线。
- 上线后网关按会话下发限速策略（见第 3 节）。

### 2.2 续期与保活

- 无感会话存在**生命周期盯梢**：会话需要流量维持，长期无流量的会话会被静默回收（"饿死"）。
- 工程对策：以周期性探测流量保活（向公网目标发包）；缺少保活时，会话被回收 → 重新接入 → 再次占用资源，形成不必要的状态抖动。若某条腿因分配不到流量而逐渐死亡，还会进一步恶化该腿的流量分配，形成恶性循环。

### 2.3 超时回收与被动失效

- 超时 / 静默回收：长时间无流量 → 会话被清除。
- 被动失效的两种典型原因：

  1. **同账号顶替**（"后到顶先到"）：同账号新设备接入，旧的无感会话被清；
  2. **端口会话集重置**：同一接入端口发生会话变动（新增 / 删除 MAC、批量重启接口、大量 DHCP 交互）时，网关可能重置该端口上的"会话集合"——保留最久最稳的会话，清除其余。表现是"某设备自己没动却掉线"。

- 诊断要点："DHCP 能拿到地址、网关也通，但数据面被拦"通常意味着**会话被拒 / 被重置**，而非链路故障；应先核对同账号其它设备是否在线，避免把正常顶替误判为故障、反复"重新接入"反而制造更多变动。

### 2.4 主动下线 / 解绑的两种形态（重点）

在设备管理页面执行"下线"类操作，实际对应两条不同的请求链，后果截然不同：

| 形态 | 动作链 | 结果 | 可恢复性 |
|---|---|---|---|
| 纯下线（只断会话） | 仅向计费 / 会话服务提交终止请求 | 会话结束，**白名单条目保留** | ✅ 设备重新接入即自动恢复 |
| 组合下线（解绑 + 断会话） | 先执行解绑类（delete）操作，成功后再终止会话（前端串行联动） | 会话终止，**白名单条目被删除** | ❌ 不可逆，需重新走绑定流程（要账号密码） |

要点：

1. 页面上的"下线 / 解绑"按钮触发的到底是哪种形态，取决于前端动作链；**解绑操作往往会级联终止会话**，把绑定与在线状态一起清掉。
2. 解绑类接口在本次调研中表现为**弱校验**：请求不含密码，对不存在的条目也返回成功（无存在性检查）——它在设计上就不是"需凭据才可执行"的操作。

### 2.5 风险场景：无感绑定被静默删除

- **场景 A（误操作）**：在设备管理页对某设备执行"下线"，命中的若是组合形态 → 白名单条目被删，用户当下无感知，直到重连时发现不再免密。
- **场景 B（级联、影响第三方）**：聚合链路中常并存多个账号的多台设备；若有人在门户对其中某台设备执行组合下线，删除的是该设备所属账号的无感绑定——**可能直接破坏他人设备的免密接入能力**，且他人无法自行恢复（恢复需要其账号密码）。
- **场景 C（无法区分）**：会话掉线后难以判断是"纯会话被清（重新接入即可恢复）"还是"绑定被删（需重新绑定）"。判据：查询该账号的白名单——MAC 仍在 = 纯会话下线；MAC 消失 = 绑定被删。
- **工程对策**：

  1. 聚合链路内所有设备的启停一律在**接入侧控制**（关 / 开接口），不触碰门户的下线功能；
  2. 周期性巡检白名单（发现条目消失即告警），防止绑定被静默删除而不自知；
  3. 涉及第三方账号设备时尤甚：任何门户侧"下线 / 解绑"操作都不可执行。

## 3. 为什么"多会话并存"是带宽合并的前提

1. **限速是会话级的，不是账号级的**：带宽令牌桶挂在会话上（网关按会话下发），同一账号下多个在线会话各自持有**独立限速桶**、互不共享。账号总带宽 ≈ 会话数 × 单会话上限。
2. **每会话独立公网出口**：在运营商级 NAT 出口下，每个会话获得独立的公网映射，多会话 = 多条互不干扰的传输通道。
3. **合并发生在会话之上**：多会话只是"原料"，带宽合并需要出口侧的分发调度（见《02 多设备网速合并原理》）。没有多会话，单会话的天花板就是带宽上限，无从合并。
4. **可靠性红利**：某条会话被回收 / 顶替时，其余会话不受影响，聚合可自动降级（三腿 → 两腿 → 单腿），不会整体断网。

## 4. 小结

- 认证模型 = 账号—设备绑定：绑定需凭据、放行看 MAC；无感机制让设备断线重连零人工。
- 会话生命周期 = 上线 → 保活 / 续期 → 超时回收 / 被动失效 → 主动下线。主动下线务必区分"纯断会话"与"解绑 + 断会话"：前者可恢复，后者不可逆。
- 多会话并存是系统原生能力，也是带宽聚合的前提；聚合的全部工程手段都建立在"会话即限速桶、会话即出口通道"这一模型之上。
