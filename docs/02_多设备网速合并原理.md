# 02 多设备网速合并原理

> 开源项目《校园网带宽聚合研究》· 原理篇 02（项目核心）
> 本文由内部调研资料脱敏重写，仅讨论"多会话带宽合并"的通用原理；文中 MAC、IP、速率等数值均为占位符或示意值，不指向任何真实环境。

## 0. 一句话结论

> 单条会话的带宽上限是单台设备的天花板；但当同一接入环境里存在多条独立会话时，可以在出口侧按"流"把流量分发到各会话，把"会话数 × 单会话上限"的带宽合并成一台设备 / 一个网段的体验。合并的正确粒度是**连接 / 流**，绝不是**包**。

## 1. 为什么能合并：会话即"桶"

- 认证网关按会话下发限速策略（令牌桶），每会话一组**独立限速桶**；
- 在运营商级 NAT 出口下，每会话获得**独立公网映射**；
- 账号并发名额允许 K 台设备同时在线 → 可用带宽 ≈ Σ（各会话上限）。

所以多会话天然是"K 份独立带宽资源"，剩下的事只有一件：**把上层流量合理地、稳定地摊到这 K 份资源上**，并对外呈现"一个出口"。

## 2. 整体架构：接入 → 汇聚 → 统一出口

```
 接入层（会话层）                汇聚层（分发层）                 出口层
 ┌──────────────┐         ┌─────────────────────┐         ┌────────────────┐
 │ 设备1 ── 会话1 │         │ 按连接/流分发：        │         │ 统一出口视图：    │
 │ 设备2 ── 会话2 │ ──────► │ · 内核策略路由          │ ──────► │ · TUN 虚拟网卡   │
 │ 设备3 ── 会话3 │         │   (multipath/mwan3)  │         │ · 代理端口        │
 │ …        …   │         │ · 应用层聚合代理        │         │ （应用只看得到    │
 └──────────────┘         │   (mihomo 类 load-     │         │   一个出口）      │
                          │    balance)           │         └────────────────┘
                          └─────────────────────┘
  每会话：独立限速桶 + 独立公网出口
```

- **接入层**：K 台设备 / 接口各自独立接入认证（手动或无感），各持一份会话——这一层只负责"制造会话"。
- **汇聚层**：把应用流量按"流"分配到会话；有网关形态与终端形态两种载体（第 5 节详述）。
- **出口层**：客户端只感知"一个出口"（虚拟网卡或代理入口），背后是多个会话在分担。

架构铁律：**先建会话、后开聚合**。会话上下文按源 IP 关联，因此必须让各链路先以真实接入形态完成认证；启用聚合（尤其是 TUN 全接管）后若需重认证，应暂停聚合，让门户流量走真实接入路径。

## 3. 分发粒度：为什么逐包轮询不可行

### 3.1 TCP 无法容忍跨会话乱序

- 把一条 TCP 流的包按逐包轮询散到两条路径：两条路径时延 / 带宽不同 → 对端收到**乱序段** → 触发重复 ACK → 发送端快速重传、拥塞窗口减半 → 吞吐塌缩到接近最差路径，严重时重传风暴甚至连接重置。
- 且每个会话拥有独立公网出口：同一 5 元组从两个公网地址交替发出，会破坏 NAT 绑定与对端的连接状态。

### 3.2 正确粒度：连接（流）

- 按连接分发：新建连接时选定一条会话，此后该连接的所有包恒走该会话——天然满足"同流同路"。代价是**单条连接的带宽 ≤ 单会话上限**，这是 TCP 语义决定的硬边界。
- 补偿方式：多连接应用（网页多资源、DASH/HLS 视频分段、多线程下载器、应用商店）天然把大量连接摊到多个桶上，整体体验即"多桶之和"。

### 3.3 对照：数据包级绑定（需要中继）

- 若目标是把**单条长连接**翻倍，只能采用数据包级绑定（如部分 bonding 代理服务 / MPTCP 类方案）：包被拆散走多条路径，由**远端中继节点**负责按序重组并统一出口——这依赖你自己无法控制的远程基础设施。
- 自建、无中继的聚合只能做到连接级；本项目的所有方案都建立在这一约束之内。

## 4. 分发算法：L4 哈希与连接轮询

### 4.1 内核路径：multipath 哈希

- 多 nexthop 的默认路由下，内核按哈希把每条流固定到某个 nexthop。**哈希字段必须包含端口（L4）**：

  - 只按源 / 目的 IP（L3）哈希时，若大量连接的目标是同一服务器 / 同一 CDN 边缘 IP，则这些连接会全部命中同一条路径 → 一腿满载、其余腿空转（某次实测中曾出现一腿吞吐近乎为零、另一腿接近满载的极端失衡；改为 L4 哈希后立即摊开）。
  - L4 哈希（Linux：`sysctl net.ipv4.fib_multipath_hash_policy=1`，可持久化）让 5 元组不同的连接散布到各 nexthop。

- 本质：按流哈希到出接口，同流恒同路，与 §3.2 的要求一致。

### 4.2 用户态路径：聚合代理的连接级轮询

- 多出口聚合代理（如 mihomo 的 load-balance 出站组）为**每条新建连接**选择一个出站：round-robin 逐连接轮流，或按目标规则哈希。
- 每个出站对应一条会话：本机会话可用"直连 + 接口绑定"表达；远端会话可用"指向另一台已认证设备上转发器的 SOCKS5 出站"表达。
- 附加能力：出站存活探测可自动跳过失效腿（三腿 → 两腿自动降级）；TUN 模式把全系统流量收进虚拟网卡，应用无感。

### 4.3 哈希 vs 轮询的统计特性（都需要意识）

- **哈希**：流 → 腿映射稳定，但存在**碰撞**——若多条重流量共享相近的 5 元组前缀，可能撞到同一腿，造成短期失衡。
- **轮询**：连接数量均衡，但**字节数可能不均**（一条长连接对比很多条短连接）。
- 两者都是"尽力统计均衡"而非精确均衡；验收标准应是"多腿同时有吞吐 + 连接分布合理"，而不是"两腿字节数相等"。

## 5. 两条实现路径的分工：网关负载均衡 vs 聚合代理

| 维度 | 网关形态（mwan3 / multipath 多 WAN） | 终端形态（mihomo 类聚合代理） |
|---|---|---|
| 解决问题 | "一个网段内多台设备，如何共享多条会话出口" | "一台机器，如何吃掉多份会话带宽" |
| 工作位置 | 软路由 / 网关，在 LAN 与多个 WAN 会话之间 | 端点设备，在应用与多个出站之间 |
| 分发机制 | 按流打标记 / 哈希选 WAN（连接级） | 按连接选出站（轮询 / 规则） |
| 会话表示 | 每个 WAN 接口 = 一条会话 | 每个出站 = 一条会话（直连绑定 / 远端 SOCKS） |
| 失效处理 | 存活跟踪，摘除失效 WAN | 出站探测，自动跳过失效腿 |
| 注意点 | 需 L4 哈希策略、回程路由、避免标记冲突；mwan3 较重型 | TUN 需相应权限；重认证时暂停；接口绑定不能跨网段时的替代（经网关 SOCKS 转发） |

- **mwan3**：用户态接管，按规则对连接打标记，靠连接标记保持连接归属；带回程跟踪与失效 WAN 摘除。灵活，但存在版本 / 行为差异的坑。
- **multipath**：纯内核，默认路由多 nexthop 按流哈希；轻量，但需正确设置 L4 哈希、回程路由，并与防火墙连接标记配合得当。
- **聚合代理**：把"统一出口"做得最彻底（应用只见一个虚拟网卡 / 代理入口），且天然适用于**单机多腿**场景。
- **两者可叠加**：网关把网内几条会话聚合成"一个出口"，聚合代理再把该出口当作一条腿与本机会话合并——多级汇聚得到更多腿。

## 6. 瓶颈分析：等效带宽的现实天花板

### 6.1 理论值

- 等效带宽理论上限 = Σ 每会话上限（K × 单桶 B）。示例：2×50M → 100M，3×50M → 150M。

### 6.2 制约一：本地物理链路

- 单端口的物理带宽是硬天花板：示例中 2×50M 聚合实测基本填满百兆端口（约 92–98M 量级）；即使桶数更多，也需要更快的物理链路（或改用多链路 / 无线组合）才能获得增量。

### 6.3 制约二：对端与内容侧

- 单条 TCP 连接受对端限制（CDN 单连接带宽、下载服务对重复下载的限流）；**验收聚合必须用多连接并发测速**——单连接永远只等于单桶。

### 6.4 制约三：链路与时段

- 高峰时段上联拥塞会让**每会话自身**降速（单会话也会跌破标称值）；聚合放大的是"相对当前单会话"的倍数，绝对值随基础速率波动。
- 对国际 / 特定目标限速的链路，用国外源验收会误判聚合失效。

### 6.5 制约四：哈希碰撞与均衡波动

- L3 哈希"假平坦"、L4 哈希仍有碰撞、轮询存在字节不均；个别腿短暂空转 / 过载属正常统计现象，不必然代表架构失效。

### 6.6 制约五：隧道单桶（境外流量）

- 经加密隧道 / 远端代理节点转发的流量表现为**单条传输 socket**（隧道的本质是一条连接）——它从本机出发只走一条会话，因此**境外隧道吞吐受单会话上限约束**：即使隧道内开多个并发下载，也只在隧道两端之间复用，无法摊到多个校园网桶上。突破需多隧道或中继式包级绑定，工程代价高；现实选择是接受"境外单桶"约束，把多桶能力留给国内直连流量。

### 6.7 制约六：会话生命周期

- 无感会话静默回收（饿死）→ 需要双向保活；
- 同账号新设备接入顶替旧会话 → 需要提前规划会话组合；
- 端口会话集重置（他人变动牵连本会话）→ 需要"变动纪律"（一次只动一个接口、间隔充分、失败长冷却）；
- 任一腿掉线导致聚合退化 → 需要自动降级而非整体断网。

### 6.8 注意：令牌桶突发（PIR）

- 令牌桶允许瞬时突发超过名义上限，实测峰值可能略超"K × 单桶"之和；**峰值不能用于容量规划**，应以统计稳定值评估。

## 7. 工程要点清单

1. **会话优先**：先以真实接入链路认证建好全部会话，再启动聚合；重认证时暂停聚合。
2. **双向保活**：本机腿（绑定源地址的探测）+ 网关腿（本地周期探测），防止"饿死回收 → 腿死 → 更分不到流量 → 更死"的循环。
3. **变动纪律**：任何 MAC / 接口 / DHCP 变动都有端口级成本；单点、低频、失败即冷却。
4. **自动降级**：分发器对失效腿自动跳过，聚合从 K 腿平滑退化到 K-1、K-2 腿，不整体断网。
5. **冷启动自动链**：开机后按序"拉起网关虚拟机 → 等待会话就绪 → 延迟启动聚合 → 保活就位"，实现清晨零人工恢复。
6. **验收方法**：多连接并发测速 + 观察多腿同时有吞吐（或经日志确认连接分布在多腿）；单连接采样不足以判定聚合生效。

## 8. 总结

- 合并的本质：K 个会话 = K 份独立限速桶 + K 条独立出口；聚合层只负责"按流分发 + 统一出口视图"。
- 分发的正确粒度是连接 / 流而非包；L4 哈希保证同一流稳定归属同一会话，避免 TCP 乱序与 NAT 绑定破坏。
- 等效带宽 = 会话数 × 单会话上限，实际受物理链路、对端限制、时段拥塞、哈希碰撞、隧道单桶与会话生命周期共同制约。
- 网关路径（mwan3 / multipath）解决"多会话共享给一个网段"，聚合代理（mihomo 类）解决"单机统一出口"，两者可叠加实现多级汇聚。
