# 04 · 健壮性设计

> 多会话聚合系统的故障模式清单与自愈体系：keepalive、断线恢复、腿级降级、白名单巡检、断电开机链条。
> 本文只讲**通用故障模型与工程套路**，不包含任何真实环境数据。

## 1. 设计目标：健壮性优先于带宽

聚合系统的收益（≈N 倍带宽）只有在"会话持续在线、桶始终满额"时才成立。实际运行中，会话会被静默回收、被变动牵连清理、被门户操作误删绑定，任何一环失效都会让聚合悄悄退化成单会话，而用户往往毫无感知。

因此健壮性设计的目标是：

1. **保住会话**：用最廉价的手段维持会话活性，打断"饿死"回路；
2. **自动恢复**：会话掉了能自动探测、分类、重连、复验，尽量减少人工；
3. **及时发现不可自动修复的损坏**（尤其是绑定被删这类不可逆事件），并告警留痕；
4. **断电/重启全自动收尾与拉起**，让"每天自动断电的环境"也能无人值守运行。

## 2. 故障模式清单

聚合链路从"物理口 → 各会话 → 出口合并代理 → 应用"每一环都可能挂。实践归纳出的故障模式如下：

| # | 故障环节 | 典型症状 | 可否预测 | 处置方向 |
|---|---|---|---|---|
| F1 | 会话被静默回收（饿死） | 网关/DHCP 正常，数据面丢包 100% | 可预测（规律复现） | keepalive 保活；被打断的回路见 §3.3 |
| F2 | 会话被"变动牵连"清理 | 自身从未变动，但在别的接口变动后被连带清除（同端口非豁免会话被清，最老最稳的会话幸存） | 不可预测 | 减少变动；被清后按 §4 单点重新接入 |
| F3 | 真身设备重新上线顶替克隆会话 | 克隆桶丢包且无法恢复，原设备活跃 | 不可预测 | 识别后停用克隆桶，与人沟通，勿反复重试 |
| F4 | DHCP 被拒 / 端口进入冷却（升级惩罚） | 连 IP 都拿不到，网关 ARP 静默 | 不可预测 | 长冷却（≥30 分钟）或物理断电重启 |
| F5 | 认证类会话过期（无感免密不适用） | 该会话出网中断，需重新走认证页 | 可预测（有生命周期） | 自动检测 + 提醒人工重认证（唯一人工步骤） |
| F6 | 网关不可达 / 上联故障 | 全网或某会话网关丢包 | 可预测 | 分级探测，区分本侧与会话级故障 |
| F7 | 聚合代理崩溃 / 启动时序错乱 | 聚合退化为单会话或全部不通；上游腿未就绪时代理启动导致 auto-detect 失败 | 部分可控 | 延迟启动 + 就绪探测 + 外部控制器可查腿 |
| F8 | 虚拟机/设备断电重启 | 全部会话重建，配置盘可能损坏 | 可预测（定时断电） | 优雅关机链 + 开机自愈链（§7） |
| F9 | 无感绑定被静默删除 | 桶丢包、网关通；白名单条目消失 | 不可预测 | 白名单基线巡检（§6），优先告警而非自动恢复 |
| F10 | 监控进程依赖宿主会话被杀死 | 恢复监控静默停止，无人值守期失明 | 可预测 | 监控逻辑迁入设备本机（cron），与宿主解耦（§8） |
| F11 | 单腿劣化被健康检查掩盖 | 某条腿丢包 30~60%，但健康检查（单次探活）仍能通过，它继续吃 1/N 流量，整体延迟被拖高 | 可预测（丢包率是渐变的） | **腿级降级**：连续多轮采样丢包率 → 摘腿；恢复达标 → 放回（§5） |

> **两条最重要的经验**：
> 1. 故障之间**表象相同、诱因不同**（"网关通 + 数据面拦"既可能是会话被清，也可能是同账号互斥竞争，还可能是绑定被删）——动手之前必须先分类，误操作会自我制造新的变动（F2 放大器）；
> 2. **任何会话变动都是端口级成本**：重认证、开关虚拟机、换 MAC 会牵连同端口的其他非豁免会话。变动要"规划成一批、一次做完、长期冻结"。

## 3. keepalive 策略

### 3.1 原理：源绑定（source-bound）探测

探测必须**明确指定探测对象**，而不是"随便 ping 一个网关"：

- 路由器侧：逐接口 `ping -I <接口名>`，并同时探测 <网关IP> 与 <DNS_IP>，把"会话有没有 IP / 网关通不通 / 数据面通不通"三个层次分开记录；
- 宿主侧：从指定网卡源地址 `ping -S <内网IP_A>` 探测 <DNS_IP>，确保探测流量真的从被保活的会话发出。

只保活"数据面健康"的会话（丢包 0% 才发维持包），避免向已死会话发包制造无效负载。

### 3.2 定时探活

- 路由器侧每 5 分钟对数据面活的接口发少量维持包：**只 ping，不做 DHCP renew、不 ifup/ifdown**——探活与"变动"严格分离，探活不计入网络的变动惩罚计分；
- 宿主侧每 4 分钟做一次源绑定 ping（保活那些在宿主机上、不在路由器管理范围内的会话）；
- 观测采样每 2 分钟一轮，记录各会话丢包率并保留滚动日志（如最近 300 行循环），出现 0% 丢包写入恢复时间戳——它是"退惩罚"信号，也是自愈流程的触发源；
- 各间隔均为可调参数，按"网络对静默回收的容忍度"与"变动惩罚敏感度"折中选取。

### 3.3 防饿死：打断"回收回路"

一个典型故障回路（F1 的机制）：

```
聚合代理全量接管流量 → 某条直连腿分配不到流量（分配失败被重试到别的腿）
→ 该会话长期零流量 → 网络侧按生命周期回收会话 → 该腿更无流量 → 饿死循环
```

- 代理仅用 mixed 端口（应用按需走直连）时，Windows 侧流量天然覆盖该会话，不会饿死；**全量 TUN 接管后**才出现饿死回路；
- 对策：源绑定 keepalive 周期性建立"该会话的流量"，等价于伪造最小活性，打断回路；
- 最优实践：**探测即保活**——周期性状态采集器（每 2 分钟对每个会话做源绑定探测）本身就构成保活流量，把"观测"与"维持"合并为一份开销，不再单独跑一个保活任务。

### 3.4 keepalive 的边界

keepalive 只能解决"会话还活着但流量不够"的问题。会话已被清（F1 后期）、被牵连（F2）、被删绑（F9）时，keepalive 无效——这时进入 §4 的恢复流程或 §6 的告警，不要无限发包自欺。

## 4. 断线自动恢复流程

恢复是**分层**的，每一层都先判断再动手：

```
探测 → 分类 → 冷却 → 单点重连 → 复验自愈
```

### 4.1 探测与分类（先诊断，后动作）

每轮观测记录每个会话的：

| 观测项 | 状态组合 | 判读 |
|---|---|---|
| DHCP 有 IP？ | 无 | F4 等级故障（冷却/断电） |
| 网关 ping 通？ | 否 | 上联/端口级故障 |
| 数据面（公网探测）通？ | 网关通但数据面拦 | 会话被清（F1/F2）/ 互斥竞争 / 绑定被删（F9） |

判定"网关通 + 数据面拦"后，还要进一步区分三种可能：查同账号其他会话是否在线（排除互斥竞争）、查白名单快照（见 §6，排除绑定被删）——**不要盲目把正常竞争当惩罚去"重新接入"，那会自我制造变动**。

### 4.2 冷却纪律（铁律）

- 两次接口变动间隔 ≥ 10 分钟；单次只动 1 个接口的 1 个配置项；
- 失败后冷却 ≥ 30 分钟，冷却期**零操作**、只读轮询；重试会加重惩罚；
- 配置变更原子化：配置一次性写完生效 → 只触发一次接口事件 → 无限期观察，禁止试错循环（每次重试都计入变动计分）；
- 端口级黑洞（IP 都拿不到）的唯一可靠恢复手段是物理断电/拔插或长时间冷却。

### 4.3 单点重连（重新接入）

对"会话被清"的桶，不在全家重启网络，而是**单点重新接入**：

```
down 该接口 → 静默观察（数十秒）→ ifup 该接口（一次干净 DHCP）
```

- 只重发一次合法的接入请求，重建会话；
- 不使用全量 network restart（会同时扰动所有会话，触发连带清理）；
- 认证类会话（F5）无法脚本化重认证：自动检测到失效 → 提示用户到认证页完成一次手动认证（全链路唯一的人工步骤）。

### 4.4 复验与自愈确认

- 重连后等待恢复信号（观测记录出现 0% 丢包 = 恢复时间戳写入）；
- 连续多轮稳定确认后才判定"恢复"，防止假恢复（恢复后立即又被清）；
- 全部恢复后进入**冻结运行**：keepalive + 观测 cron 维持，零手工变动。

## 5. 腿级降级：分流熔断与手动停用

断线恢复（§4）处理的是「整条腿不通」；本节处理更隐蔽的一类——**腿还在，但已经劣化**（F11）。

### 5.1 为什么单次健康检查不够

聚合出口多为 `load-balance` / 哈希分流，腿级健康检查通常是「单次探活 + 固定周期」。
一条丢包 40% 的腿仍有约 60% 的概率通过单次检查，于是它继续吃 1/N 的流量：
每一次分到它的请求都有概率重传/超时，整体延迟与抖动被拖高，而监控面板上它还是"在线"。

**结论：健康检查管「完全不通」，熔断管「通但丢包严重」，两者互补，不能互相替代。**

### 5.2 判定：连续多轮采样，而不是看单次

按桶（腿）每轮探测 N 次，算丢包率，然后看**连续轮数**：

| 条件 | 动作 |
|---|---|
| 丢包率 ≥ 阈值（默认 50%）连续 `trip_after`（默认 2）轮 | 隔离该腿 |
| 丢包率 ≤ 恢复阈值（默认 10%）连续 `recover_after`（默认 3）轮 | 放回该腿 |
| 中间值（10%~50%） | 不动计数——避免抖动被累计成"坏"或"好" |

三个关键护栏：

1. **单轮抖动不误判**：任何一轮达标就把"连续不合格"计数清零；
2. **不允许摘到空**：活跃腿数必须始终 > `keep_min`（默认 1），全摘等于把聚合出口打死；
3. **失败即回滚语义**：摘腿/放腿的动作没真正执行成功（命令没配、非 0 退出、超时），
   **就不记录为"已隔离"**——界面状态必须等于实际拓扑，否则就是自欺（"面板说摘了、腿上还挂着"）。

### 5.3 执行：判定与动手分离

判定逻辑是通用的，**怎么摘腿是环境相关的**（改 provider 文件并热更新？调管理面 API？重启上游？）。
因此这类工具的正确做法是：**自己只做判定与编排，动手交给一条用户配置的命令**。
项目里 `tools/bucket_console/` 就是这么做的：

- 熔断按桶采样 → 判定 → 执行 `actions.isolate_leg` / `actions.restore_leg`；
- 随附 `leg_ctl.py` 给出「节点列表在独立文件 + provider 热更新」这一类的参考实现：
  母本全量定义 → 按剔除集合渲染生效文件 → `PUT /providers/proxies/<名>` 热更新，
  带 `keep_min` 保护、原子写 + 备份、幂等、`--dry-run`、漂移检测与 `sync` 重建；
- 没有可用摘腿手段时**留空即可**：熔断仍会采样并在界面显示丢包率，只是不真的摘腿。

### 5.4 手动降级：停用某条腿

自动熔断之外，还有一类需求是"我要主动把某条腿停掉"（正在换设备、室友要打游戏、临时排障）。
做法是把**停用**做成桶的一个字段（`enabled: false`），而不是删配置：

- 停用后该桶不探测、不动作、界面置灰，状态显示「已停用」；
- 配置仍在，恢复只需改回一个布尔值；
- 停用集合与熔断摘除集合**取并集**再渲染，两条路径互不干扰（手动停用不会被熔断的恢复流程放回）。

> 这一节的判定参数、护栏与执行方式在 `tools/bucket_console/README.md` §3.7 / §3.8 有完整的配置说明。

## 6. 白名单基线巡检

### 6.1 动机：不可逆的静默删除

门户的"设备下线"操作存在两种形态：

- **纯会话下线**：只终止会话，无感绑定保留 → 重新接入即可恢复；
- **组合下线**：先解绑再终止会话，**无感绑定被删除** → 不可逆，需重新做绑定（需要更高权限上下文）。

若有人在门户对某个会话执行了组合下线，或者管理页误操作，克隆出来的桶会"看起来是丢包"，但根因是绑定没了。**掉线表象无法区分二者**，而绑定被删是唯一不能用自动重连修复的故障——必须主动巡检。

### 6.2 方法与处置

- **定期拉取快照**：通过白名单枚举接口（免鉴权即可查询）定期抓取各相关账号的白名单条目，与上次快照对比，diff 非空即记录；
- **事件告警**：某条目从快照中消失 → 产生"绑定被删"事件（状态文件 + 事件日志，滚动保留）；
- **处置分级**：绑定仍在 = 纯会话下线 → 走 §4 自动重连；绑定消失 = 被删 → **告警优先，不做自动恢复**（自动重绑需要更高权限，且存在误绑风险），提示人工决策；
- 巡检频率远低于探活（如每小时），只做只读查询，不产生任何会话变动。

## 7. 优雅关机 / 开机自愈链条（夜间断电场景）

### 7.1 场景与风险

夜间定时断电的环境里，宿主机、虚拟机每天被强制关闭：

- 会话全部释放 → 无感会话开机后会自动恢复（免密），认证类会话需重新认证；
- 真实风险是**非正常断电损坏配置盘**（路由器配置与脚本在可写层）与**开机时序错乱**（代理先于上游就绪启动，导致腿失效 auto-detect 失败）。

### 7.2 收尾链（断电前）

按时间顺序自动执行：

1. 先让路由器**同步文件系统并干净关机**（`sync` 后 poweroff），把可写层的数据刷盘落稳再断电；
2. 停止聚合代理，释放接管；
3. 宿主机延迟若干秒后关机 —— 确保不晚于断电时刻。

### 7.3 开机链（登录后自动拉起）

依赖"登录事件"触发（任务要求交互式会话），按依赖顺序延迟执行：

1. 延迟数十秒 → 启动路由器虚拟机；
2. 轮询等待其管理口可达（SSH/管理端口就绪）→ 拉起各无感会话接口（单点 ifup，触发干净 DHCP → 无感免密自动恢复）；
3. 等待代理上游（如路由器上的转发服务端口）**可达后**再启动聚合代理 —— 避免"代理先起、上游未就绪"导致的自动发现失败；
4. 代理启动完成 → 用外部控制器核对各会话腿状态，确认聚合恢复。

### 7.4 演练与验收

- 断电链必须**实际演练**（模拟一次完整断电 + 开机），不能只看脚本；
- 演练观察点：管理口就绪时序、无感会话恢复顺序、代理启动前上游端口是否已监听；
- 验收标准：开机后无需人工干预即恢复 N 会话聚合（认证类会话除外，属已知人工步骤）；
- 注意陷阱：开机后**单连接**采样出口全落同一会话会被误判为"没聚合"——判断聚合恢复必须用并发测速或逐会话观测（见文档 03 §5）。

## 8. 监控的独立性：把观测逻辑迁到设备本机

早期实践把恢复监控放在宿主机做远程轮询（每 60 秒 SSH 进路由器采样），踩到两个坑：

1. 远端转发脚本在宿主机侧反复出现编码/引号问题；
2. 宿主机侧的会话级进程随宿主环境重启被杀，无人值守期"失明"。

**改造原则**：一切周期性观测、判读、自愈动作都在路由器本机用 cron 承载（纯 ASCII 脚本 + 滚动日志 + 恢复时间戳）；宿主机只做**单命令只读查询**（一条 SSH 命令拿状态），不再承载长驻监控进程。观测与恢复从此与宿主机的会话生命周期解耦。

## 9. 操作纪律速查

| 纪律 | 说明 |
|---|---|
| 配置原子化 | 一次写完生效，一次接口事件，禁止试错循环 |
| 变动间隔 ≥10 分钟 | 含改 MAC、ifup/ifdown、DHCP renew 一切变动 |
| 失败冷却 ≥30 分钟 | 冷却期零操作、只读轮询 |
| 先分类再动手 | 网关通+数据面拦 ≠ 一定是惩罚；先查互斥、查白名单 |
| 不动门户的"组合下线" | 对克隆会话只走接口侧启停，绑定才保留 |
| 只克隆"历史久 + 真实离线"的白名单设备 | 避免新 MAC 首现、避免顶替在用设备 |
| 冻结运行 | 全活后零变动，keepalive + 观测 cron 自治维持 |
| 绑定被删 ≠ 丢包 | 查快照 diff，告警而非自动重连 |
| 单腿劣化 ≠ 整链故障 | 丢包高的腿用腿级降级（熔断/停用）摘掉，别整链重启（§5） |
| 摘腿要可回滚 | 隔离/放回都必须幂等、有备份、有 `keep_min` 保护，且失败时界面不许"假装已隔离" |

## 10. 小结

- 故障模式中，**不可预测且不可自动修复**的只有少数几类（真身设备顶替、绑定被删、升级惩罚）；其余都可被"探测→分类→冷却→单点重连→复验"的流程自动消化。
- keepalive 的价值在于打断饿死回路、维持会话活性，但它救不了已被清的会话——恢复流程才是防线的主干。
- 白名单基线巡检专门对付"掉线表象掩盖不可逆损坏"的场景，把不可修复的故障提前暴露为告警。
- 腿级降级（分流熔断 / 手动停用）对付的是"腿没死但已经不好用"：它把「判定」与「动手」分离，
  判定通用、动手交给环境相关的一条命令，并用 `keep_min`、幂等与"失败不假装成功"保证可回滚。
- 断电环境下的优雅关机与开机自愈链，把"每天被断电打断"从运维负担变成无人值守的例行事务。
