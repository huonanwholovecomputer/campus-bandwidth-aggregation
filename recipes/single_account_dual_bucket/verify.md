# 验证与排查：单账号双桶

> 判断"双桶聚合到底有没有生效"以及"某条腿掉了怎么处理"。
> 详细的测速方法论见仓库根 [experiments/verify_aggregation.md](../../experiments/verify_aggregation.md) 与 [docs/03](../docs/03_限速机制与等效带宽.md)。

---

## 1. 先分清：单连接 ≠ 聚合已生效

- **单连接永远只走一个桶**（≤ 单会话上限）——用单连接测速判断聚合，结论永远是"没聚合"；
- 判断聚合是否生效，**必须用并发测速**（多连接下载 / 8 路并行），看合计是否 ≈ 2 × 单会话上限；
- 或用日志 / 出口交替确认连接被分布到两桶。

## 2. 验收流程（并发测速）

1. **单桶基准**：分别测桶1、桶2 各自约等于单会话上限（`<单会话上限>` 量级）；
2. **并发聚合**：开 TUN 后多连接并行下载（多线程下载器开足够线程数），合计应 ≈ 2 × 单会话上限；
   - 若合计仍 ≈ 单会话上限：多半是**连接没被分布到两桶**（见 §4 排查）；
3. **出口交替检查**（若两桶独立出口）：多连接轮询采样出口地址，应看到两个不同出口交替；
   - 若出口相同（网络按账号聚合出口），以**带宽叠加**为准，不要被"出口相同"误导。

## 3. 逐会话观测

同时观察两桶各自的实时速率是否都接近单会话上限、"近似叠加"——这比只看总和更能定位是哪条腿没出力。

---

## 4. 故障排查速查

| 症状 | 原因 | 处理 |
|---|---|---|
| 聚合后仍 ≈ 单桶 | 连接未分到两桶（哈希碰撞 / 单一出口路由 / load-balance 未生效） | 核对 load-balance 组成员、L4 哈希策略；用并发测速（单连接永远等于单桶） |
| 桶2 掉线：网关/DHCP 通、数据面拦 | 会话被静默回收（饿死）/ 被变动牵连清理 / 同账号互斥 | 先分类再动手（docs/04 §4）：查同账号其它会话是否在线、查白名单快照；按冷却纪律单点"重新接入"（down→静默→ifup 一次） |
| 桶2 掉线且真机活跃 | 真机设备上线顶替克隆会话（F3） | 停用克隆桶，与设备错开；勿反复重试 |
| 连 IP 都拿不到 | 端口级冷却 / DHCP 被拒（升级惩罚） | 长冷却 ≥30 分钟，只读轮询；严重时物理断电重启 |
| 桶2 会话过期（非无感，需重新认证） | 认证类会话生命周期到期（F5） | 自动检测 + 到认证页手动重认证（全链路唯一人工步骤） |
| 桶1 饿死（TUN 后直连腿分不到流量） | 全量接管后 DIRECT 腿无流量被回收（饿死回路） | 宿主侧源绑定保活（docs/04 §3.3）；混合端口模式天然覆盖，可缓解 |
| 聚合代理重启后"静默退回单桶" | 非提权重启，TUN 创建被拒 | 用管理员/root 重启；重启后核对虚拟网卡是否真的存在 |
| 聚合代理启动时桶2 不可用 | 桶2 上游未就绪时就启动了代理 | 等 OpenWrt SOCKS 端口就绪后再启动代理（延迟启动 + 就绪探测） |

---

## 5. 关键纪律

- **先分类再动手**："网关通 + 数据面拦"≠ 一定是惩罚，可能是互斥竞争或绑定被删——误操作会自我制造新的变动；
- **冷却纪律**：任何 MAC / 接口变动间隔 ≥10 分钟；失败冷却 ≥30 分钟，冷却期零操作、只读轮询；
- **冻结运行**：两桶全活后零变动，保活 + 观测 cron 自治维持；
- **不要用门户"组合下线"删绑定**（会连带删无感绑定，不可逆）；桶的启停只在 OpenWrt 侧做。
