# 搭建步骤：单账号双桶

> 目标：**只用你自己的一个账号**，让两条会话同时在线（直连本体桶1 + 同账号第二桶桶2），
> 在宿主机出口侧合并成约 2 × 单会话带宽。
> 本文件是分步配方；所有 `<占位符>` 替换规则见 [docs/00](../docs/00_脱敏与贡献规范.md)。

---

## §0 前置核查（先做，别跳）

这一步决定"这个配方在你这套环境是否成立"，也决定后面怎么动手。

### 0.1 账号并发名额

- 在"在线设备 / 会话管理"页面（或实测）确认：**你的账号能否 ≥ 2 台设备同时在线**。
- 名额上限记为 `<并发上限>`；本配方需要 `<并发上限> ≥ 2`。
- 若只有 1 个名额，聚合前提不成立，配方不适用。

### 0.2 白名单里可用的第二台"自有离线设备"

- 打开你账号的白名单（无感/免密设备列表），找一台**你拥有、且当前真实离线（或未占用名额）**的设备，取其 MAC 记为 `<MAC_B>`。
  - 推荐：闲置手机、旧电脑、虚拟机等——必须是"历史久 + 真实离线"的，避免新设备首次接入触发异常。
  - **绝不**用他人设备的 MAC（合规边界，见 README §6）。
- 你的直连本体（插墙口那台）的 MAC 记为 `<MAC_A>`，它正在线（桶1）。

> 为什么必须"真实离线"：无感放行是纯 MAC 单因子，但若该设备真机同时在线，可能与本配方中的克隆会话互顶 / 冲突（详见 docs/04 的 F3 故障模式）。

### 0.3 同账号多会话能否并存（关键规则）

不同网络的规则不同，常见可并存组合有：

| 组合 | 说明 |
|---|---|
| 两台**不同设备类型**（如 PC + 手机）的无感会话 | 常分属不同会话池（PC 池 / 移动池），可并存 |
| **手动认证**会话 + **无感**会话 | 认证轨与无感轨互斥较弱，常可并存 |
| 同类型无感会话（如两台 PC） | 常"后到顶先到"互斥，**不可**并存 |

- 动手前先确认你的账号属于哪种组合（用你已有设备实测，或按 docs/01 §1.3 / docs/02 判断）；
- 若你的第二桶和直连本体是"会互斥的同类型无感"组合，则需要让其中一个走手动认证轨，或改用"不同设备类型"的白名单条目；
- **变动纪律**（docs/04 §8）：任何 MAC / 接口变动都有端口级成本，先规划成"一批、一次做完、长期冻结"。

### 0.4 物理链路

- 确认墙口物理链路带宽 ≥ 2 × 单会话上限，否则合不出来（瓶颈在物理层，见 docs/03 §6.2）。

### 0.5 材料清单

| 材料 | 用途 |
|---|---|
| 一台宿主机（Windows / Linux） | 跑聚合代理，直连本体 = 桶1 |
| 一台轻量软路由（本配方用 OpenWrt VM，128MB 内存即可） | 承载桶2（克隆 MAC + SOCKS + 分桶） |
| 一个虚拟化平台（如 VMware / KVM） | 跑 OpenWrt VM，桥接到墙口网线所在网段 |
| 聚合代理（mihomo，兼容经典 clash 配置） | 宿主侧把两桶合并 |

## §1 桶1：直连本体在线

你的宿主机直插墙口网线，完成认证，形成会话1。两种方式：

- **无感（免密）**：宿主机 MAC `<MAC_A>` 在你的白名单内 → 插线即自动在线，无需任何操作；
- **手动认证**：首次插线被重定向到认证门户 → 输入账号密码 → 会话建立。

完成后确认：宿主机能正常出网，且在线会话管理页能看到这 1 条会话（桶1）。

> 本步先**不要**开任何聚合/TUN——会话上下文按源 IP 关联，先裸连认证好，再谈合并（docs/02 铁律）。

---

## §2 桶2：OpenWrt 上克隆"你账号第二台离线设备"的 MAC

在 OpenWrt VM 上，用你账号白名单里第二台离线设备的 MAC `<MAC_B>` 克隆出一个 WAN 口，触发无感免密放行，形成会话2。

### 2.1 前置

- OpenWrt VM 已桥接到与墙口同一网段（即能拿到校园内网 IP）；
- 第二台设备真机**已离线**（§0.2）；
- OpenWrt 上已安装 `microsocks`（SOCKS 服务）与 `ip`/`uci`（默认自带）。

### 2.2 克隆并上线

直接使用模板脚本 [templates/openwrt_second_bucket.sh](templates/openwrt_second_bucket.sh)（占位符替换后执行），或按下面手动：

```bash
ssh root@<OpenWrt管理IP>
# 1) 给一个 WAN 网口克隆你账号第二台离线设备的 MAC
uci set network.wan2.device='<物理WAN接口>'
uci set network.wan2.proto='dhcp'
uci set network.wan2.macaddr='<MAC_B>'
uci commit network
ifup wan2            # 触发换 MAC + DHCP 续约
sleep 10
ip link show <物理WAN接口> | grep ether          # 期望显示 <MAC_B>
ip -4 addr show <物理WAN接口> | grep inet        # 期望拿到校园内网 IP
# 2) 无感放行验证（走该网卡源 IP 直测连通性，期望放行码 204）：
curl -s -m 10 -o /dev/null -w '%{http_code}\n' --interface <物理WAN接口> <探活目标URL>
#    期望 204；若返回重定向/门户页 => 说明白名单未命中 / 账号侧问题，回退
```

- **无感命中即放行**：只要 `<MAC_B>` 在你账号白名单、且真机离线，克隆后 DHCP 拿到 IP 即免密出网，形成第二个独立会话（桶2）；
- 若没放行：先核对白名单是否含 `<MAC_B>`、真机是否真离线、是否触发同账号互斥（§0.3）。

### 2.3 起 SOCKS 出口（把桶2交给宿主机用）

OpenWrt 上跑一个绑定该 WAN 口、可让宿主机经内网访问的 SOCKS 服务：

```bash
IP=$(ip -4 addr show <物理WAN接口> | grep -o 'inet [0-9.]*' | head -1 | awk '{print $2}')
nohup /usr/bin/microsocks -p <SOCKS端口-B> -i <SOCKS监听地址> -b "$IP" -q >/dev/null 2>&1 &
ss -tlnp 2>/dev/null | grep <SOCKS端口-B>     # 确认在监听
```

- `<SOCKS端口-B>` 用高位端口（如 1080）；
- 若 OpenWrt 默认路由本身已是"多 nexthop"（多会话分桶），SOCKS 出口的连接会被内核按 L4 哈希自动分到各腿；单账号双桶时通常只有一条 WAN 腿承载桶2，`-b` 绑定源地址可让出口确定走该会话；
- 模板脚本里给了完整的多腿 multipath + L4 哈希配置，单桶可直接用其中的 SOCKS + 绑定部分。

### 2.4 验证桶2

- OpenWrt 上 `curl --interface <物理WAN接口> <探活目标URL>` → 204；
- 从宿主机经 SOCKS 试一下：
  ```bash
  curl -x socks5h://<OpenWrt管理IP>:<SOCKS端口-B> -m 10 -o /dev/null -w '%{http_code}\n' <探活目标URL>
  ```
  期望 204（socks5h 用远端解析，避免本地 DNS 干扰）。

## §3 聚合：宿主机把两桶合并

在宿主机用聚合代理（mihomo）把桶1（DIRECT）+ 桶2（SOCKS → OpenWrt）合并成"一个出口"。

### 3.1 先冒烟（不开 TUN）

把 [templates/host_aggregate.yaml](templates/host_aggregate.yaml) 填好占位符，先 `tun.enable: false`、只留 `mixed-port`，启动：

```bash
mihomo -d <配置目录> -f <配置目录>/config.yaml
```

然后多连几次，确认出口在桶1 / 桶2 之间**轮流交替**：

```bash
for i in $(seq 1 8); do curl -x <本地地址>:<混合端口> -s -m 10 <出口查询URL>; echo; done
```

- 若两桶独立出口：应看到两个不同出口交替出现；
- 若出口相同（网络按账号聚合出口），改用**带宽叠加**判断（见 [verify.md](verify.md)）。

### 3.2 开 TUN（全系统接管）

- 以**管理员 / root** 重启 mihomo（TUN 需要权限；非提权重启会静默退回直连单桶，见模板风险提示）；
- `tun.enable: true` 后，系统所有流量经虚拟网卡按连接分发到两桶；
- **重认证 / 门户**时暂停 TUN，让门户流量走真实接入路径。

### 3.3 保活与自愈

- 会话需要周期性流量维持（防"饿死"回收），且桶2被清后要能自动重连：
  - 通用故障模式与恢复流程见 [docs/04](../docs/04_健壮性设计.md)；
  - OpenWrt 侧建议用 cron 每数分钟对数据面活着的接口发少量维持包（只 ping，不 DHCP、不 ifup），并每 2 分钟记录丢包率；
  - 宿主直连本体（桶1）若走 TUN 后分不到流量可能饿死，需在宿主侧做源绑定保活；
  - 具体模板可参考仓库根 [templates/keepalive.service](../../templates/keepalive.service) 的写法。

## §4 收尾

1. 按 [verify.md](verify.md) 做**并发测速验收**（单连接永远只等于单桶，必须并发测）；
2. 全部稳定后**冻结运行**：零 MAC / 接口变动，让保活 + 观测 cron 自治维持；
3. 涉及开关机（如夜间断电）的优雅收尾/开机自愈链，见 [docs/04 §6](../docs/04_健壮性设计.md)。

---

## §5 回退

- 停聚合：关 TUN / 停 mihomo → 回到单桶直连，不影响会话；
- 停桶2：OpenWrt 上 `uci set network.wan2.disabled='1'; uci commit; ifup wan2`，pkill SOCKS；
- 白名单不删：克隆失败/不再用时**不要**用门户"组合下线"删绑定（会连带删无感绑定，不可逆），只在 OpenWrt 侧启停接口即可（docs/04 §5）。
